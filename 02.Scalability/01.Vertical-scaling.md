# Vertical Scaling (Scaling Up)

## 1. What Is Vertical Scaling?

**Vertical scaling means making an existing server more powerful** by adding more CPU, RAM, or other resources.

Instead of adding more servers, you upgrade the machine you already have.

**Example:** Your e-commerce application runs on a server with 8 GB RAM and 2 CPU cores. As traffic increases, the server struggles. You upgrade it to 64 GB RAM and 16 CPU cores.

The same application can now handle more users without necessarily changing its code.

## 2. Real-World Example: Black Friday Sale

Imagine your e-commerce website handles 1,000 concurrent users on normal days.

During Black Friday, you expect 10,000 concurrent users. However, your existing server starts struggling at just 2,000 users:

- Pages take 5 seconds to load.
- Some requests time out.
- Users have a poor experience.

**Solution:** Upgrade to a more powerful server with additional CPU and RAM.

The bigger server can handle more concurrent requests, improving performance without introducing multiple application servers.

*Analogy:* When your family grows from 3 to 6 members, you could buy a second car or replace your small car with a bigger SUV. Vertical scaling is like choosing the bigger SUV.

## 3. Why Is Vertical Scaling Not Always the Answer?

Vertical scaling is simple, but it has three major limitations.

### A. Increasing cost

A more powerful server usually costs more, and high-end configurations can become disproportionately expensive.

Illustrative monthly cloud-server costs:

| Server configuration | Monthly cost |
|---|---:|
| 1 GB RAM, 1 vCPU | $8 |
| 8 GB RAM, 2 vCPUs | $67 |
| 384 GB RAM, 96 vCPUs | $4,600 |
| 3,904 GB RAM, 128 CPUs | $26,688 |

These are example prices, not current cloud-provider quotes.

Notice that the cost does not always increase proportionally with resources. Specialized, high-end machines can be particularly expensive.

### B. Hardware limits

You cannot keep upgrading a server forever. Eventually, you reach the maximum CPU, RAM, or processing capacity available on a single machine.

Moore's Law, proposed by Gordon Moore in 1965, observed that transistor counts on integrated circuits roughly doubled every two years. This helped drive decades of computing improvements.

However, transistor miniaturization faces physical and engineering challenges, so we cannot rely on hardware becoming infinitely more powerful.

### C. A single point of failure

If your entire application depends on one server and that server fails, the application may become unavailable.

A bigger server gives you more capacity, but **it does not automatically give you better fault tolerance**.

## 4. When Does One Server Become Insufficient?

Consider a hypothetical social network processing 4 million likes per second.

Suppose each like requires just 1 millisecond of CPU processing.

\[
4{,}000{,}000 \times 0.001 = 4{,}000
\]

That means the system needs **4,000 CPU-seconds of processing every second** — approximately 4,000 fully utilized CPU cores, assuming one millisecond of CPU time per like.

This excludes other work, such as database operations, cache updates, notifications, and timeline updates, unless those are already included in the assumed processing time.

Even a hypothetical server with 448 cores would fall far short of this requirement.

**Key takeaway:** Some workloads eventually require more processing capacity than a single machine can provide. Adding more powerful hardware alone cannot solve the problem indefinitely.

## 5. When Does Vertical Scaling Make Sense?

### A. Small and medium-sized applications

For websites and applications with manageable traffic, one powerful server may be sufficient.

It is easier to deploy, monitor, debug, and maintain than a distributed system.

### B. Databases

Many companies initially run their database on one powerful server.

This avoids the additional complexity of distributed databases, such as network latency, consistency challenges, and operational overhead.

A well-configured database server with sufficient RAM and CPU can handle substantial workloads. Sharding or other distribution techniques can be introduced when the workload justifies them.

### C. Applications that are difficult to distribute

Some legacy enterprise applications, scientific workloads, and financial systems were designed to run on a single machine.

Distributing them may require expensive architectural changes or a significant rewrite. Vertical scaling can be a practical way to extend their useful life.

## 6. Real-World Example: Stack Overflow

Stack Overflow has historically demonstrated how a relatively small number of powerful servers, combined with careful optimization, can serve a large audience.

The original example describes 9 web servers, each with 64 GB RAM and 12 CPU cores.

The important lesson is not the exact server count, which can change over time. It is that **efficient code, caching, optimized database queries, and powerful hardware can go a long way** before a system needs extensive horizontal scaling.

Keeping frequently accessed data in RAM can also reduce slower disk reads and improve query performance.

## 7. Advantages and Disadvantages

| Advantages | Disadvantages |
|---|---|
| Simple to implement and manage | Limited by maximum hardware capacity |
| Often requires no application-code changes | High-end servers can be very expensive |
| No extra network communication between application instances | A single server can become a single point of failure |
| Easier monitoring, debugging, backup, and recovery | Upgrades may require downtime |
| Immediate performance improvement when resources are the bottleneck | Limited ability to distribute workloads geographically |
| Avoids much of the complexity of distributed systems | Can create dependence on specialized hardware or a cloud provider |

**Important:** Vertical scaling does not always require downtime. Some cloud upgrades support live or near-live changes, but other upgrades require a restart, migration, or maintenance window.

## 8. What About Downtime During Upgrades?

Suppose your application runs on one server and that server needs to be upgraded.

If the upgrade requires stopping the application, users may experience downtime.

You can schedule the upgrade during low-traffic hours, but that only reduces the impact; it does not eliminate downtime.

With multiple application servers behind a load balancer, you can often upgrade instances one at a time while the remaining instances continue serving requests.

This is one reason horizontal scaling can improve availability.

## 9. When Should You Move to Horizontal Scaling?

Consider horizontal scaling when:

- **You reach hardware limits:** One server cannot provide enough capacity.
- **Costs become excessive:** Adding another server is more economical than upgrading to a larger machine.
- **Availability matters:** You need other servers to continue working if one fails.
- **Downtime is unacceptable:** You need to upgrade or maintain servers without taking the entire application offline.
- **You need geographic distribution:** You want to serve users from different regions with lower latency.

### What about Friendster?

Friendster, an early social network, is often cited as an example of the difficulties of scaling a growing web application.

As its popularity grew, performance and reliability problems contributed to a poor user experience, while competitors gained ground.

The broader lesson is that repeatedly adding hardware cannot compensate indefinitely for architectural and performance problems. However, Friendster's decline had multiple causes, so it should not be attributed solely to vertical scaling.

## 10. The Typical Scaling Journey

Many applications follow this progression:

1. **Start small:** Run the application on one server.
2. **Scale vertically:** Add CPU and RAM as demand grows.
3. **Optimize:** Improve code, caching, database queries, and resource usage.
4. **Scale horizontally:** Add more servers when one machine is no longer sufficient or availability requirements demand it.
5. **Use a hybrid approach:** Keep powerful individual servers for components such as databases while distributing other components across multiple machines.

There is no universal user-count threshold for moving to horizontal scaling. The right time depends on workload, resource utilization, cost, latency, and availability requirements.

## Final Takeaway

**Vertical scaling = make one server bigger.**

It is simple, effective, and often the right starting point. But a single machine has a maximum capacity, high-end hardware can become expensive, and one server can become a point of failure.

When these limitations become significant, consider horizontal scaling — adding more servers instead of relying entirely on one increasingly powerful machine.
