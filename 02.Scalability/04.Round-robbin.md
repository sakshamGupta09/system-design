# Load Balancing Algorithms

- A load balancing algorithm decides **which server should handle the next incoming request**.
- How do we distribute incoming traffic to various servers.

## Round Robin

- Distribute requests equally among servers in a repeating sequence.
- Suppose we have three application servers:

```text
Requests: R1  R2  R3  R4  R5  R6
             |
        Load Balancer
         /    |    \
       S1     S2     S3

Distribution:
S1 → R1, R4
S2 → R2, R5
S3 → R3, R6
```

- The pattern repeats: `S1 → S2 → S3 → S1 → ...`
- With three identical servers and 9,000 requests/second, each receives approximately 3,000 requests/second.

### Pros
- Simple, fast and predictable.
- Works well when servers have similar capacities and requests have similar processing costs.

### Cons
- Treats powerful and weak servers equally.
- Ignores current CPU usage, queue length and request complexity.
- Equal request counts do not guarantee equal workloads.

**When to use:** When servers have similar capacities and handle relatively similar requests.

## Weighted Round Robin (WRR)

- What if servers have different capacities?
- Suppose two old servers have 8 CPU cores each, while a new server has 32 cores. Giving each server one-third of the traffic may overload the older servers and waste the new server's capacity.
- Assign each server a weight based on its capacity. A higher weight means a larger share of requests.

### How It Works

Suppose the server weights are `1, 1, 4`.

```text
             Load Balancer
             Total weight = 6
             /     |      \
          S1 (1) S2 (1)  S3 (4)

Traffic:  16.7%  16.7%   66.7%
```

For every six requests, approximately:
- Server 1 receives 1 request.
- Server 2 receives 1 request.
- Server 3 receives 4 requests.

For 9,000 requests/second:

| Server | Weight | Requests/second |
|---|---:|---:|
| Server 1 | 1 | 1,500 |
| Server 2 | 1 | 1,500 |
| Server 3 | 4 | 6,000 |

**Formula:**

`Traffic share = Server weight / Total weight`

### Pros
- Supports servers with different capacities.
- Allows traffic distribution to be controlled through configuration.
- Useful for gradual deployments and canary releases.
- Can help distribute traffic across different instance types or regions.

### Cons
- Basic WRR uses predetermined weights rather than actual server load.
- A server receiving expensive requests can still become overloaded.
- Requires weight tuning when capacity or traffic patterns change.

**When to use:** When servers have different capacities or when you need to control traffic percentages.

## Weighted Round Robin for Canary Deployments

- A **canary deployment** means gradually sending traffic to a new application version instead of moving all users at once.

Example: Releasing a new API version.

| Stage | Old Version Weight | New Version Weight | New-Version Traffic |
|---|---:|---:|---:|
| Initial rollout | 19 | 1 | 5% |
| Expand rollout | 15 | 5 | 25% |
| Halfway | 10 | 10 | 50% |
| Almost complete | 1 | 19 | 95% |
| Complete | Removed | Active | 100% |

Monitor errors and latency at each stage. If the new version performs poorly, reduce its weight or stop sending it traffic.

**Why it matters:** You can limit the impact of bugs and gradually increase exposure without changing application code, provided the infrastructure supports traffic-weight updates.

## 5. Limitations of Both Algorithms

- Round Robin and Weighted Round Robin distribute requests according to a predetermined pattern. They do not inherently understand how much work each request requires.

Consider:

- Homepage request: takes 50 ms.
- PDF report request: takes 5 seconds.
- Both count as one request, but the PDF request requires much more processing.
- If a server receives several expensive requests, it may become overloaded while other servers remain underutilized.

They also do not inherently react to:
- Sudden CPU or memory spikes.
- Long request queues.
- Garbage collection pauses.
- Slowdowns caused by resource-intensive operations.
