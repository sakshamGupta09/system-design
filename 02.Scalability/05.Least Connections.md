# Load Balancing Algorithms – Advanced Algorithms

## 1. Least Connections

**Idea:** Send the next request to the server currently handling the fewest active connections.

Unlike Round Robin, which distributes requests equally, Least Connections considers how busy each server actually is.

### How it works

1. The load balancer checks the active connections on each server.
2. It selects the server with the fewest active connections.
3. The request is forwarded to that server.
4. Once a connection finishes, its count decreases.

**Example:**

| Server | Active connections |
|---|---:|
| Server A | 10 |
| Server B | 4 |
| Server C | 7 |

The next request goes to **Server B** because it has the fewest active connections.

### Why is it better than Round Robin?

- Not all requests require equal processing time.
- A product listing request might take 100ms, while checkout might take 3 seconds.
- Round Robin ignores this difference.
- Least Connections naturally accounts for long-running connections.

### Weighted Least Connections

An extension of Least Connections that considers both:
- Active connections.
- Server capacity (weight).

**Example:**

| Server | Capacity | Active connections | Utilization |
|---|---:|---:|---:|
| A | 1,000 | 400 | 40% |
| B | 2,000 | 900 | 45% |

Even though Server A has fewer connections, it has lower capacity utilization.

Therefore, Server A receives the next request.

### Pros
- Adapts to varying request processing times.
- Prevents servers from accumulating too many long-lived connections.
- Works well for WebSockets and other persistent connections.
- Weighted version accommodates servers with different capacities.

### Cons
- Requires tracking active connections.
- Connection count doesn't always represent actual resource usage (CPU, memory, bandwidth).
- Adds some overhead to load-balancer decision-making.

**When to use:** Applications with long-lived connections, WebSockets, streaming, and workloads with varying connection durations.

## 2. IP Hash

**Idea:** Use the client's IP address to consistently route requests to the same backend server.

The load balancer hashes the client's IP address and uses the result to select a server.

### How it works

1. Client sends a request.
2. Load balancer extracts the client's IP address.
3. It applies a hash function to the IP.
4. The hash determines the backend server.
5. Requests from the same IP generally reach the same server, as long as the server pool remains unchanged.

**Example:**

Client IP: `192.168.1.100`

    Client IP
        |
        v
    Hash Function
        |
        v
    Hash = 456789
        |
        v
    456789 % 5 = 4
        |
        v
    Server 4

All subsequent requests from this IP go to Server 4.

### Why is this useful?

It provides **session affinity (sticky sessions)**.

Consider a traditional e-commerce application:

- User adds products to their shopping cart.
- Cart data is stored in Server 4's local memory.
- Subsequent requests from the same IP reach Server 4.
- The user's cart remains accessible without replicating session data across servers.

### Pros
- Provides automatic session affinity.
- Avoids needing to replicate session data across backend servers.
- Useful when applications maintain local session state.

### Cons

**1. Uneven load distribution**
- Multiple users behind the same corporate NAT share one public IP.
- They all get routed to the same backend server.
- One server can become overloaded while others remain idle.

**2. Changing client IPs**
- Mobile users frequently switch between Wi-Fi and cellular networks.
- Their IP address changes, potentially routing them to another server.
- Their locally stored session may no longer be accessible.

**3. Scaling problems**
- Uses a mapping such as `hash(IP) % number_of_servers`.
- Adding or removing a server changes the modulo operation.
- Most clients may get mapped to different servers.
- This causes session loss and cache misses if state is stored locally.

**When to use:** When session affinity is required and client IPs are relatively stable. Avoid relying on it as the primary session-management mechanism for mobile-heavy applications.

## 3. Consistent Hashing

**Idea:** Distribute clients or data across servers while minimizing redistribution when servers are added or removed.

It solves a major problem with traditional hashing: **changing the number of servers can remap almost every client.**

### Problem with Traditional Hashing

Suppose we have 5 servers.

    Server = Hash(key) % 5

Now, we add a sixth server.

    Server = Hash(key) % 6

The mapping changes for most keys.

**Consequences:**
- Sessions may become unavailable.
- Local caches become invalid.
- Large amounts of data may need redistribution.
- Newly selected servers can experience a cache-miss spike.

### How Consistent Hashing Works

Imagine a circular hash space (hash ring), where positions range from 0 to 1 million.

**Step 1: Place servers on the ring**

Each server is hashed to a position on the ring.

**Step 2: Hash the client or data key**

The client key is also hashed to a position on the same ring.

**Step 3: Find the responsible server**

Starting from the client's position, move clockwise until you encounter the first server.

That server handles the request.

### Example

- Server A → 100,000
- Server B → 400,000
- Server C → 700,000
- Client → 250,000

Moving clockwise from 250,000, the first server is Server B.

Therefore, the client is assigned to Server B.

### What happens when a server is added?

Suppose Server D is added at position 550,000.

- Only keys in the interval between Server B and Server D move to Server D.
- Other keys continue mapping to their existing servers.
- There is no need to redistribute everything.

**Key intuition:** Only the keys belonging to the affected portion of the ring need to move.

With evenly distributed servers, adding one server to a cluster of five typically moves approximately 1/6 of the keys, rather than reshuffling almost everything.

### Virtual Nodes (Important)

A basic consistent hashing ring can distribute keys unevenly because physical servers may not be uniformly positioned.

**Virtual nodes solve this problem.**

- Each physical server is assigned multiple positions on the ring.
- These positions are called virtual nodes (vnodes).
- Keys are distributed across these positions.
- This improves load distribution.
- When a physical server is added or removed, only its associated virtual-node ranges need redistribution.

### Pros
- Minimizes data redistribution when servers are added or removed.
- Reduces cache invalidation and disruption.
- Supports horizontal scaling.
- Virtual nodes improve distribution and accommodate different server capacities.

### Cons
- More complex to implement than simple hashing.
- Without virtual nodes, distribution can be uneven.
- Requires managing the hash ring and membership changes.

**When to use:** Distributed caches, distributed databases, partitioning, and systems where data or clients should remain mapped to the same servers despite cluster changes.

Examples include Cassandra and Dynamo-style distributed systems.

## 4. Quick Comparison

| Algorithm | Primary objective | Best suited for |
|---|---|---|
| Least Connections | Balance active connections | Long-lived connections |
| Weighted Least Connections | Balance based on connection count and capacity | Heterogeneous servers |
| IP Hash | Maintain session affinity | Stable client IPs |
| Consistent Hashing | Minimize redistribution | Distributed systems and caching |

---

## 5. Interview Takeaways

1. **Round Robin vs Least Connections:** Round Robin distributes requests equally; Least Connections considers active connections.
2. **Least Connections vs Weighted Least Connections:** Weighted Least Connections also considers differences in server capacity.
3. **IP Hash:** Provides session affinity but can cause uneven distribution due to NAT and problems when client IPs change.
4. **Traditional Hashing vs Consistent Hashing:** Traditional modulo hashing remaps many keys when the server count changes; consistent hashing minimizes remapping.
5. **Virtual Nodes:** Improve key distribution and help balance load across physical servers.
6. **Important distinction:** Consistent hashing is primarily a key-to-server mapping strategy, whereas Least Connections is a request-routing strategy based on current server load.

### Remember the Intuition

- **Least Connections** → Send traffic to the least busy server.
- **Weighted Least Connections** → Consider how busy a server is relative to its capacity.
- **IP Hash** → Same client IP, same server.
- **Consistent Hashing** → Add or remove servers without reshuffling everything.
