# Stateless Service Design

- State is any user information we store to serve the next request better. Like Login information, shopping cart, files saved on local disk.
- In a single server setup, we can store user states in server's local memory because every request goes to a single server. But with horizontal scaling, this leads to a massive problem as a request can go to any server now.
- User State should not be stored in any server's local memory. Because the next request might go to a different server.
- We should instead store the state in an external shared system like Redis, DBs and Object storage which all servers can access.

Key Benefits:
- Any server can handle any request.
- Servers don't depend on previous requests to handle the next ones.
- All servers can access the same shared data.

## Why do we need Stateless Service Design

- For Easy Horizontal Scaling.
- We can spin up servers on demand which can start handling requests immediately without any state synchronization required.
- Failiure : Servers can crash without losing session information.


## Trade-offs and Limitations

- **Additional Latency:** Fetching data from Redis or a database introduces network latency compared to local memory.
- **Infrastructure Complexity:** You need external systems like Redis, message queues and object storage.
