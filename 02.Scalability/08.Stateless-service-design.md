# Stateless Service Design

## 1. What is the problem?

Imagine an application running on 3 servers:

- Server A
- Server B
- Server C

A user sends a request to Server A. The server stores the user's session in its local memory.

When the next request arrives, the load balancer sends it to Server B.

**Problem:** Server B doesn't know anything about the user because the session was stored in Server A's memory.

This creates problems when requests are handled by different servers.

## 2. What is Stateless Service Design?

**A stateless service does not store user-specific information between requests in its own memory.**

Instead, it stores important state in external, shared storage systems.

This means:
- Any server can handle any request.
- Servers don't depend on previous requests.
- All servers can access the same shared data.

**Important:** Stateless doesn't mean the application has no state. It means the application servers don't maintain critical user state locally.

## 3. How does it work?

Imagine a user logs into an application.

1. User logs in through Server A.
2. Server A verifies the credentials.
3. It generates a signed authentication token (JWT) containing the user's information.
4. The token is sent back to the user.
5. On the next request, the user sends this token.
6. The load balancer sends the request to Server B.
7. Server B validates the token, extracts the user ID and fetches any required data from the database.

**Key idea:** Server B doesn't need to know which server handled the previous request.

## 4. Where is the state stored?

Instead of storing everything in application server memory, use shared external storage.

| Type of Data | Where to Store |
|---|---|
| User sessions | Redis |
| User profiles and shopping carts | Database (MongoDB/PostgreSQL) |
| Uploaded files and images | Object storage (Amazon S3) |
| Temporary shared cache | Redis / Memcached |
| Background and async jobs | Message queues (Kafka / RabbitMQ) |

This allows any application server to access the required information.

## 5. Why do we need Stateless Service Design?

**1. Easy Horizontal Scaling**
- Add more servers whenever traffic increases.
- New servers can immediately handle requests.
- No need to transfer user sessions between servers.

**2. Better Fault Tolerance**
- If Server A crashes, another server can handle the next request.
- User sessions and important data aren't lost with that server.

**3. Better Load Distribution**
- Requests can be distributed across servers freely.
- No need to send users to the same server every time.

**4. Easier Deployments**
- Servers can be replaced or restarted without transferring user sessions.
- New servers can start handling requests immediately.

## 6. Important Design Considerations

**1. Avoid Local File Storage**

- Don't store uploaded files on individual application servers.
- Store them in shared object storage like S3.
- Store the file URL in the database.

**2. Use Shared Caching**

- Avoid relying only on individual servers' local caches.
- Use Redis or Memcached so all servers can access the same cached data.

**3. Coordinate Scheduled Jobs**

- Imagine 10 application servers running the same daily email job.
- Without coordination, all 10 might execute it.
- Use distributed locks, a dedicated job scheduler or separate worker services to prevent duplicate execution.

## 7. Trade-offs and Limitations

- **Additional Latency:** Fetching data from Redis or a database introduces network latency compared to local memory.
- **Infrastructure Complexity:** You need external systems like Redis, databases and object storage.
- **External Dependencies:** If shared storage becomes unavailable, application servers might not be able to access the required state.

**Exception:** Some components, such as WebSocket connections and local performance caches, can remain stateful when necessary. The important thing is that critical user state should not depend on a particular application server.

## 8. Real-world Example

Think of a restaurant.

**Stateful approach:**
- You always need to speak to the same waiter.
- Only that waiter remembers your previous orders.

**Stateless approach:**
- Your orders are recorded in a central system.
- Any waiter can check the system and serve you.

The central system acts like a shared database.

## 9. Key Takeaway

**Stateless service design means application servers don't depend on locally stored user information between requests. Required information comes from the request itself or shared external storage.**

This makes applications easier to scale horizontally, distribute traffic and recover from server failures.
