# Stateless Service Design

- User specific information like sessions and assets should not be stored in server memory.
- Because the next request might go to a different server which cannot access the previous stored data.
- We should instead store the state in an external shared system like Redis and Object storage which all servers can access.

Key Benefits:
- Any server can handle any request.
- Servers don't depend on previous requests to handle the next ones.
- All servers can access the same shared data.

## How does it work?

Imagine a user logs into an application.

1. User logs in through Server A. Server A verifies the credentials.
2. It generates a signed authentication token (JWT) containing the user's information. The token is sent back to the user.
3. On the next request, the user sends this token.
4. The load balancer sends the request to Server B.
5. Server B validates the token, extracts the user ID and fetches any required data from the database.
6. Server B doesn't need to know which server handled the previous request.

## Why do we need Stateless Service Design?

For Easy Horizontal Scaling.

## Trade-offs and Limitations

- **Additional Latency:** Fetching data from Redis or a database introduces network latency compared to local memory.
- **Infrastructure Complexity:** You need external systems like Redis, message queues and object storage.
- **External Dependencies:** If shared storage becomes unavailable, application servers might not be able to access the required state.
