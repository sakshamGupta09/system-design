# Circuit Breaker Pattern

- Prevents a failing service from continuously receiving requests, giving it time to recover.
- Instead of continuously waiting for the failed Service, the Order Service can fail fast and handle the situation gracefully.

## 2. Let's understand with an example

Imagine an e-commerce application with two services:

- **Order Service:** Processes customer orders.
- **Payment Service:** Processes payments.

Whenever a customer places an order, the Order Service calls the Payment Service.

### Normal flow

```text
  ┌────────────────┐
  │  Order Service │
  └────────┬───────┘
           │
           │ Payment Request
           ▼
  ┌────────────────┐
  │ Payment Service│
  └────────┬───────┘
           │
           │ Payment Success
           ▼
  ┌────────────────┐
  │  Order Service │
  └────────────────┘
```

Everything works fine until the Payment Service starts experiencing problems.

Without a circuit breaker:

1. Order Service keeps sending payment requests.
2. Payment Service keeps failing.
3. Requests start piling up.
4. Resources get exhausted due to repeated failures.
5. The problem can spread to the Order Service and potentially other services.

**One failing service can bring down the entire application!**

## 3. How does Circuit Breaker solve this?

It monitors failures and automatically changes its state.

There are three states:

### 1. CLOSED — Normal state

- Requests flow normally to the Payment Service.
- The circuit breaker monitors failures.
- If failures cross a configured threshold, it transitions to OPEN.

```text
  ┌────────────────┐
  │  Order Service │
  └────────┬───────┘
           │
           ▼
  ┌────────────────┐
  │Circuit Breaker │
  │    CLOSED      │
  └────────┬───────┘
           │
           │ Requests allowed
           ▼
  ┌────────────────┐
  │ Payment Service│
  └────────────────┘
```

### 2. OPEN — Circuit tripped

- Requests are blocked immediately.
- The Payment Service is not called.
- The failing service gets time to recover.
- After a configured waiting period, the circuit transitions to HALF-OPEN.

```text
  ┌────────────────┐
  │  Order Service │
  └────────┬───────┘
           │
           ▼
  ┌────────────────┐
  │Circuit Breaker │
  │     OPEN       │
  └────────┬───────┘
           │
           X  Requests blocked
           │
           ▼
  ┌────────────────┐
  │ Payment Service│
  └────────────────┘
```

### 3. HALF-OPEN — Testing recovery

- After waiting for some time, the circuit allows a few test requests.
- These requests check whether the Payment Service has recovered.

```text
  ┌────────────────┐
  │  Order Service │
  └────────┬───────┘
           │
           ▼
  ┌────────────────┐
  │Circuit Breaker │
  │   HALF-OPEN    │
  └────────┬───────┘
           │
           │ Limited test requests
           ▼
  ┌────────────────┐
  │ Payment Service│
  └────────────────┘
```

**What happens next?**

- If test requests succeed → CLOSED (normal operation).
- If test requests fail → OPEN (block requests again).

### State transition diagram

```text
       ┌──────────────────┐
       │      CLOSED      │
       │  Requests allowed│
       └────────┬─────────┘
                │
                │ Failures cross threshold
                ▼
       ┌──────────────────┐
       │       OPEN       │
       │  Requests blocked│
       └────────┬─────────┘
                │
                │ Waiting period expires
                ▼
       ┌──────────────────┐
       │    HALF-OPEN     │
       │  Test requests   │
       └────────┬─────────┘
                │
          ┌─────┴─────┐
          │           │
     Tests pass   Tests fail
          │           │
          ▼           ▼
       CLOSED        OPEN
```

## 4. Real-world example

Imagine the Payment Service fails 5 consecutive times.

| Event | Circuit state | What happens? |
|---|---|---|
| Initially | CLOSED | Requests pass through |
| 5 failures | OPEN | Requests are blocked |
| After 30 seconds | HALF-OPEN | A few test requests are allowed |
| Test succeeds | CLOSED | Normal requests resume |
| Test fails | OPEN | Requests are blocked again |

*The numbers are illustrative; actual thresholds and waiting periods are configurable.*

## 5. Why do we need Circuit Breaker?

Three important benefits:

1. **Prevents cascading failures:** One failing service doesn't bring down other services.
2. **Allows recovery:** Gives the failing service time to recover instead of continuously overwhelming it.
3. **Fail fast:** Avoids wasting time and resources waiting for requests that are likely to fail.

## 6. Circuit Breaker vs Retry

These two concepts solve different problems.

- **Retry:** Try the failed request again, assuming the failure might be temporary.
- **Circuit Breaker:** Stop sending requests when a service is consistently failing.

They are often used together. However, retries should be limited and carefully configured to avoid making an overloaded service even worse.

---

## Remember this simple intuition

A Circuit Breaker is like an electrical safety switch for microservices.

- When a service is healthy → Allow requests.
- When a service keeps failing → Stop requests.
- After some time → Test whether it has recovered.
