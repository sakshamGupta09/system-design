# Service Discovery Pattern

- Service Discovery is a pattern that allows services to automatically find the network locations (IP address and port) of other services.
- Instead of hardcoding IP addresses, services dynamically discover where other services are running.

## Problem

Imagine an e-commerce application with multiple microservices: Order Service, Payment Service and User Service

- The Order Service needs to communicate with the Payment Service. How does Order Service know where the Payment Service is running?
- The Order Service could simply hardcode the IP address of Payment service.

Now consider these situations:

1. What if its IP address changes?
2. A service can have multiple instances to handle more traffic.
3. New instances are added and old instances are removed as traffic changes.

Hardcoding IP addresses becomes difficult to maintain.

## 3. How Does Service Discovery Work?

Service Discovery typically uses a **Service Registry**.

A Service Registry is a central place that maintains information about available services and their network addresses.

Think of it as a phone directory for services.

### Step 1: Service Registration

When a Payment Service instance starts, it registers its IP address and port with the Service Registry.

### Step 2: Service Registry Maintains Instances

If multiple Payment Service instances are running, the registry maintains their addresses.

```text
Service Registry

Payment Service:
  - 192.168.1.10:8080
  - 192.168.1.11:8080
  - 192.168.1.12:8080
```

### Step 3: Service Lookup

When the Order Service needs to communicate with the Payment Service, it queries the registry.

The registry returns the list of available, healthy instances.

### Step 4: Service Communication

The Order Service connects to one of the available Payment Service instances.

### Step 5: Health Checks

The registry tracks whether service instances are healthy.

If an instance crashes or becomes unhealthy, it is marked unavailable and should no longer receive traffic.

**Complete Flow:**

```text
Payment Service Instances
          |
          | Register themselves
          v
    Service Registry
          ^
          |
          | Service Lookup
          |
      Order Service
          |
          | HTTP Request
          v
  Payment Service Instance
```

## 4. Types of Service Discovery

There are two common approaches.

### A. Client-Side Discovery

In this approach, the client service is responsible for finding and selecting a service instance.

**How it works:**

1. Order Service queries the Service Registry.
2. Registry returns available Payment Service instances.
3. Order Service selects an instance using a load-balancing algorithm (e.g., Round Robin or Least Connections).
4. Order Service directly sends the request to that instance.

**Advantages:**
- No additional network hop through a load balancer.
- Client can control instance selection and load balancing.
- Local caching can avoid querying the registry for every request.

**Disadvantages:**
- Every client needs service discovery logic.
- Requires additional client libraries and maintenance.

**Example:** Netflix Eureka.

### B. Server-Side Discovery

In this approach, a Load Balancer handles service discovery and instance selection.

**How it works:**

1. Order Service sends a request to the Load Balancer.
2. Load Balancer identifies available Payment Service instances.
3. It selects an instance using a load-balancing algorithm.
4. It forwards the request to that instance.

**Advantages:**
- Clients don't need service discovery logic.
- No special discovery libraries are required in client services.
- Discovery and load balancing are handled centrally.

**Disadvantages:**
- Adds an extra network hop through the Load Balancer.
- The Load Balancer becomes an important infrastructure component.

**Example:** AWS Elastic Load Balancing.

## 5. How Are Services Registered?

There are two common approaches.

### A. Self-Registration

The service registers itself with the Service Registry when it starts.

It periodically sends a **heartbeat** to indicate that it is still alive.

If heartbeats stop, the registry marks the instance as unhealthy.

### B. Third-Party Registration

An external component handles service registration instead of the service registering itself.

**Example:** Kubernetes automatically tracks running Pods and updates service endpoints when Pods become available or unavailable.

The application doesn't need to handle registration itself.

## 6. Service Discovery in Kubernetes

Kubernetes provides built-in service discovery using DNS.

Imagine your Payment Service has five running Pods.

Instead of remembering the IP address of each Pod, other services can simply communicate using:

```text
http://payment-service:8080
```

**What happens behind the scenes?**

1. Kubernetes provides a DNS name for the Payment Service.
2. DNS resolves that name to the Kubernetes Service IP.
3. The Kubernetes Service routes traffic to healthy, ready Pods.
4. If a Pod becomes unhealthy, it is removed from the available endpoints.
5. If new Pods become ready, they are automatically added.

The calling service doesn't need to know which Pod is currently running or what its IP address is.

## 8. Challenges to Consider

- **Registry failure:** The registry is a critical component. If it becomes unavailable, services may struggle to discover other services. Production registries need redundancy.
- **Stale information:** Cached service addresses may become outdated when instances change.
- **Health checks:** Health checks and heartbeats must detect failed instances without overloading the registry.

## 9. Key Takeaways

Remember these important concepts:

1. **Service Discovery:** Helps services automatically find each other.
2. **Service Registry:** Maintains service addresses and availability information.
3. **Service Registration:** Services or external components register service instances.
4. **Service Lookup:** A client or load balancer finds available instances.
5. **Client-Side Discovery:** Client finds and selects an instance.
6. **Server-Side Discovery:** Load balancer finds and selects an instance.
7. **Health Checks:** Help prevent traffic from reaching unhealthy instances.

**The main idea:**

Instead of hardcoding IP addresses, services dynamically discover each other. This makes microservices easier to scale, deploy and maintain.
