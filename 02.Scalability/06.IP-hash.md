# IP Hash

- Use a client's IP address to decide which server should handle their requests.
- It applies a hash function to the client's IP address and uses the result to select a backend server.
- Requests coming from the same client IP address are consistently directed to the same server.

### How it works

1. Client sends a request.
2. Load balancer extracts the client's IP address.
3. It applies a hash function to the IP.
4. The hash determines the backend server.
5. Requests from the same IP generally reach the same server, as long as the server pool remains unchanged.

**Example:**

Client IP: `192.168.1.100`

    Client IP
        |
        v
    Hash Function
        |
        v
    Hash = 456789
        |
        v
    456789 % 5 = 4
        |
        v
    Server 4

All subsequent requests from this IP go to Server 4.

### Why is this useful?

It provides **session affinity (sticky sessions)**.

Consider a traditional e-commerce application:

- User adds products to their shopping cart.
- Cart data is stored in Server 4's local memory.
- Subsequent requests from the same IP reach Server 4.
- The user's cart remains accessible without replicating session data across servers.

### Pros
- Provides automatic session affinity.
- Avoids needing to replicate session data across backend servers.
- Useful when applications maintain local session state.

### Cons

**1. Uneven load distribution**
- Multiple users behind the same corporate NAT share one public IP.
- They all get routed to the same backend server.
- One server can become overloaded while others remain idle.

**2. Changing client IPs**
- Mobile users frequently switch between Wi-Fi and cellular networks.
- Their IP address changes, potentially routing them to another server.
- Their locally stored session may no longer be accessible.

**3. Scaling problems**
- Uses a mapping such as `hash(IP) % number_of_servers`.
- Adding or removing a server changes the modulo operation.
- Most clients may get mapped to different servers.
- This causes session loss and cache misses if state is stored locally.

**When to use:** When session affinity is required and client IPs are relatively stable. Avoid relying on it as the primary session-management mechanism for mobile-heavy applications.
