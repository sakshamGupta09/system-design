# QPS and Server Estimation

- Estimate the incoming work per day, estimate how much work one server can do, and calculate how much capacity you need.
- QPS measures how many requests a system processes per second.

## How to Calculate QPS

We need two things:
- Number of daily active users (DAU).
- Average number of requests per user per day.

**Formula:**

Average QPS = Total daily requests ÷ 86,400 (For easier mental math, approximate 86,400 seconds as **100,000 seconds**).

### Example: Twitter-Like Application

Assume:
- 300 million daily active users.
- Each user reads 100 tweets per day.

**Step 1: Calculate daily read requests**

300 million × 100 = 30 billion requests/day.

**Step 2: Calculate average read QPS**

30 billion ÷ 100,000 = **300,000 QPS**.

### Average QPS vs. Peak QPS

Traffic is not uniform throughout the day. More users may be active during peak hours or major events.

For initial estimates, assume peak traffic is 2–3 times the average.

Peak QPS = Average QPS × Peak multiplier

In our example:

300,000 × 3 = **900,000 peak read QPS**.

Major events can cause even larger spikes.

### Read QPS vs. Write QPS

Assume the application receives 500 million tweets per day.

Average write QPS = 500 million ÷ 100,000 = **5,000 QPS**.

At 3× peak traffic, that becomes 15,000 QPS.

The read-to-write ratio is:

300,000 ÷ 5,000 = **60:1**.

This means the system handles approximately 60 reads for every write.

**Why does this matter?** A read-heavy system needs to optimize read performance, often through caching and read replicas, rather than scaling reads and writes in the same way.

*These are illustrative assumptions, not actual Twitter traffic figures.*

## 3. Server Estimation

Once we know the QPS, we can estimate how many servers are needed.

**Formula:**

Number of servers = Required QPS ÷ QPS handled per server

The key question is: How much traffic can one server handle?

It depends on the operation, hardware, implementation, and latency requirements.

| Workload | Illustrative capacity per server |
|---|---:|
| Simple or cached operations | 50,000–100,000 QPS |
| API requests with moderate logic | 5,000–10,000 QPS |
| Complex or resource-intensive operations | 100–1,000 QPS |

These are rough starting assumptions, not fixed industry benchmarks. Always validate them through load testing.

### Example: Estimating API Servers

Suppose:
- Peak traffic = 100,000 QPS.
- Each server handles 10,000 QPS at the required performance level.

Required servers = 100,000 ÷ 10,000 = **10 servers**.

This is the theoretical minimum. Real systems need additional capacity.

## 4. Account for Utilization and Redundancy

### A. CPU Utilization

Running servers at 100% utilization leaves little room for traffic spikes and can increase response times.

Suppose we target 70% utilization.

Required servers = 10 ÷ 0.7 ≈ 15 servers.

### B. Redundancy and Failures

We also need spare capacity to handle server failures and maintenance.

If we add 20% extra capacity:

15 × 1.2 = 18 servers.

**Practical estimate: 18 servers**, rather than the theoretical minimum of 10.

For stricter availability requirements, we may need additional capacity to survive failures in an entire availability zone or region.

> **Interview tip:** Start with the theoretical server count, then account for utilization, traffic spikes, and failure scenarios.

## 5. Example: Video Streaming Capacity

For streaming systems, concurrent users may be more useful than QPS because each user maintains a long-lived stream.

Assume:
- 200 million subscribers.
- 50 million concurrent viewers at peak.
- One server supports 10,000 concurrent streams.

Required servers = 50 million ÷ 10,000 = 5,000 servers.

Adding 20% extra capacity:

5,000 × 1.2 = **6,000 servers**.

If we also need to tolerate 10% of servers failing, we must size the fleet so the remaining servers can still handle the required load. Simply adding 10% may not be sufficient; the exact buffer depends on the failure scenario.

This estimate covers streaming capacity only. Authentication, recommendations, billing, and other services need separate estimates.

*The numbers are illustrative, not actual Netflix infrastructure figures.*

## 6. How Caching Reduces Database Load

A database can become a bottleneck when too many requests reach it.

Caching reduces the number of requests that need database access.

**Formula:**

Database QPS = Total QPS × (1 − Cache hit rate)

Example:
- Application traffic = 100,000 QPS.
- Cache hit rate = 90%.

Database QPS = 100,000 × 10% = **10,000 QPS**.

The cache absorbs 90,000 requests per second, leaving only 10,000 for the database.

This can significantly reduce database load and infrastructure costs.

### What About Database Connections?

Database connections are a limited resource. Connection pooling allows requests to reuse connections instead of opening a new connection for every request.

For example, if 200 connections each process one request every 100 milliseconds:

- Requests per connection per second = 1 ÷ 0.1 = 10.
- Theoretical throughput = 200 × 10 = 2,000 requests/second.

This assumes each connection is continuously busy and each request holds it for exactly 100 milliseconds. Actual throughput depends on query execution, contention, connection wait time, and database resources.

**Important:** More connections or database instances do not automatically mean more throughput. Use connection pooling, caching, query optimization, and read replicas where appropriate.

## 7. Geographic Distribution

Global systems distribute traffic across regions to reduce latency and improve availability.

Suppose total capacity is 1,000 servers:

| Region | Traffic share | Servers |
|---|---:|---:|
| US | 30% | 300 |
| Europe | 25% | 250 |
| Asia | 35% | 350 |
| Other regions | 10% | 100 |
| **Total** | **100%** | **1,000** |

Each region must also have sufficient spare capacity to handle local traffic spikes and failures. Traffic distribution alone does not determine the final server count.

## 8. Cost Estimation

Infrastructure efficiency directly affects operating costs.

Suppose one cloud server costs $100–$500 per month.

For 1,000 servers:

- Monthly cost = $100,000–$500,000.
- Annual cost = $1.2 million–$6 million.

This excludes additional expenses such as bandwidth, storage, databases, and managed services.

**Why does optimization matter?** Reducing resource consumption can lower infrastructure costs without sacrificing performance or reliability.

## 9. Quick Reference: Hardware Capacity

These figures provide rough intuition, not guaranteed capacity.

| Resource | Illustrative reference |
|---|---|
| CPU core | Thousands of simple operations/second, depending heavily on workload |
| 32-core server | Capacity varies widely with workload and implementation |
| Network interface | 10 or 25 Gbps are common data-center link speeds |
| SSD | Can deliver tens of thousands to hundreds of thousands of IOPS, depending on the device and workload |
| HDD | Often around 100–200 random IOPS |

Do not use hardware specifications alone to predict application QPS. Benchmark the actual workload.

## 10. A Simple Interview Framework

When estimating infrastructure, follow this sequence:

1. **Estimate users and behavior:** How many users, and how many requests per user?
2. **Calculate average QPS:** Daily requests ÷ 86,400.
3. **Estimate peak QPS:** Average QPS × an assumed peak multiplier.
4. **Estimate per-server capacity:** Use a reasonable assumption based on the workload.
5. **Calculate the baseline server count:** Peak load ÷ per-server capacity.
6. **Add headroom:** Account for utilization, spikes, and failures.
7. **Optimize and estimate cost:** Consider caching, database bottlenecks, regional distribution, and infrastructure expenses.

**The key takeaway:** Estimate the load first, determine the capacity needed to handle it, and then add enough headroom to keep the system fast and reliable.
