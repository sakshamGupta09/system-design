# QPS and Server Estimation

- Estimate the incoming work per day, estimate how much work one server can do, and calculate how much capacity you need.
- QPS tells us how many requests a system handles per second.


## Calculate Average QPS

**Formula:**

Average QPS = Total daily requests ÷ 86,400

For easier mental math, approximate 86,400 seconds as 100,000.

**Example:**

- 1 million daily active users.
- Each user reads 100 tweets per day.

Daily requests = 1 million × 100 = 100 million.

Average QPS = 100 million ÷ 100,000 = **1,000 QPS**.

## Average QPS vs. Peak QPS

Traffic is not uniform throughout the day. During peak hours or major events, requests increase.

For estimation, assume peak traffic is 2–3 times the average.

**Peak QPS = Average QPS × Peak multiplier**

Example: 1,000 × 3 = **3,000 peak QPS**.

The multiplier depends on the system's traffic patterns.

## Read QPS vs. Write QPS

- **Read:** Fetching data, such as reading a tweet.
- **Write:** Creating or updating data, such as posting a tweet.

Suppose a system handles 300,000 read QPS and 5,000 write QPS.

Read-to-write ratio = 300,000 ÷ 5,000 = **60:1**.

This means 60 reads occur for every write. Read-heavy systems often benefit from caching and read replicas.

## Server Estimation

Once we estimate peak traffic, we can calculate how many servers are needed.

**Formula:**

Required servers = Peak QPS ÷ Capacity per server

Server capacity depends on the workload, hardware, and performance requirements.

**Example:**

- Peak traffic = 10,000 QPS.
- One server handles 2,000 QPS.

Required servers = 10,000 ÷ 2,000 = **5 servers**.

This is the theoretical minimum. Real systems need extra capacity.

## Account for Utilization and Redundancy

Servers should not run at full capacity all the time. Spare capacity helps handle traffic spikes and maintain response times.

If we target 70% utilization:

Effective capacity per server = 2,000 × 70% = 1,400 QPS.

Required servers = 10,000 ÷ 1,400 ≈ **8 servers**.

We may also need additional capacity to survive server failures or regional outages.

**Key idea:** Estimate the minimum capacity first, then add enough headroom for performance and reliability.

## How Caching Reduces Database Load

Caching stores frequently requested data in a faster location, avoiding unnecessary database requests.

**Formula:**

Database QPS = Total QPS × (1 − Cache hit rate)

**Example:**

- Application traffic = 10,000 QPS.
- Cache hit rate = 90%.

Database QPS = 10,000 × 10% = **1,000 QPS**.

The cache handles 9,000 requests per second, reducing the database load by 90%.

Actual savings depend on which requests can be cached.

## 5. Database Connections

Database connections are limited resources. Connection pooling allows requests to reuse existing connections instead of opening new ones repeatedly.

**Example:**

If a request holds a database connection for 100 milliseconds:

- One connection can theoretically process 10 requests per second.
- 200 continuously busy connections can theoretically process 2,000 requests per second.

Actual throughput depends on query complexity, database capacity, and contention.

**Key idea:** More connections do not automatically mean more throughput. Use connection pooling, caching, query optimization, and read replicas where appropriate.

## 6. Cost Estimation

Suppose one cloud server costs $100–$500 per month.

For 1,000 servers:

- Monthly cost = $100,000–$500,000.
- Annual cost = $1.2 million–$6 million.

This excludes bandwidth, storage, databases, and other services.

**Why does efficiency matter?** Reducing resource usage can significantly lower infrastructure costs without sacrificing performance.

## 7. System Design Interview Approach

Follow these steps when estimating infrastructure:

1. **Estimate daily requests:** Number of users × requests per user.
2. **Calculate average QPS:** Daily requests ÷ 86,400.
3. **Estimate peak QPS:** Average QPS × peak multiplier.
4. **Estimate server count:** Peak QPS ÷ capacity per server.
5. **Add headroom:** Account for utilization, traffic spikes, and failures.
6. **Optimize costs:** Consider caching, database bottlenecks, and infrastructure expenses.

**Remember:** Estimate the workload first, calculate the required capacity, and then add enough headroom to keep the system fast and reliable.
