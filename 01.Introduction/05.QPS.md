# Back-of-the-Envelope Calculations: QPS and Server Estimation

## 1. Why Do We Need These Calculations?

Before designing a system, we need to estimate:

- **Traffic:** How many requests will the system receive?
- **Infrastructure:** How many servers are required?
- **Cost:** How much will it cost to run the system?

## 2. QPS (Queries Per Second)

QPS measures how many requests a system processes per second. It helps us estimate the load on our infrastructure.

### Average QPS

**Formula:**

Average QPS = Daily Requests / 86,400

For easier mental calculations, approximate 86,400 seconds as 100,000 seconds.

**Example: Twitter read traffic**

Assume:
- 300 million daily active users (DAU).
- Each user reads 100 tweets per day.

Daily requests = 300M × 100 = 30B

Average QPS = 30B / 100,000 = **300,000 QPS**

### Peak QPS

Traffic varies throughout the day, so systems must handle peak traffic, not just average traffic.

**Formula:**

Peak QPS = Average QPS × Peak Factor

Assuming a peak factor of 3:

300,000 × 3 = **900,000 QPS**

A factor of 2–3 is a rough starting assumption. Special events can cause much larger spikes.

### Read vs. Write QPS

Suppose users publish 500 million tweets per day.

Write QPS = 500M / 100,000 = **5,000 QPS**

| Metric | Average QPS |
|---|---:|
| Reads | 300,000 |
| Writes | 5,000 |
| Read-to-write ratio | 60:1 |

**Why does this matter?** Read-heavy systems benefit from caching and read replicas, while write-heavy systems need efficient write processing.

## 3. Server Estimation

Once we know the peak traffic, we estimate how many servers are needed.

**Formula:**

Servers Required = Peak QPS / Capacity per Server

Server capacity depends on the workload.

| Workload | Illustrative capacity per server |
|---|---:|
| Simple or cached operations | 50K–100K QPS |
| API requests with application logic | 5K–10K QPS |
| Complex operations | 100–1K QPS |

These are rough assumptions, not universal benchmarks. Actual capacity depends on hardware, request complexity, and performance requirements.

### Utilization and Redundancy

**Why not run servers at 100% capacity?**

High utilization can increase response times and leave no room for traffic spikes or server failures.

Suppose 100 servers are required at full capacity:

- At 70% utilization: 100 / 0.7 ≈ 143 servers.
- Add a 20% capacity buffer: 143 × 1.2 ≈ **172 servers**.

This is a simplified estimate. For strict failure tolerance, verify that enough capacity remains when servers fail.

### Example: Video Streaming

Suppose 50 million users are watching videos simultaneously, and each server supports 10,000 concurrent streams.

Base servers = 50M / 10,000 = 5,000

With a 20% capacity buffer:

5,000 × 1.2 = **6,000 servers**

This estimates streaming capacity only. Authentication, recommendations, profiles, and billing require additional infrastructure. Real streaming platforms also use CDNs to deliver video efficiently.

## 4. Database Capacity and Caching

### Why Is the Database a Bottleneck?

Databases have limited connection capacity and processing throughput.

Suppose a database has 200 connections, and each request holds a connection for 100 ms.

- Each connection theoretically handles 10 requests/second.
- 200 connections theoretically handle 2,000 requests/second.

This is a simplified estimate, not a universal database limit.

### How Does Caching Help?

A cache serves frequently requested data without querying the database every time.

**Formula:**

Database QPS = Total QPS × (1 − Cache Hit Rate)

Suppose the system receives 100,000 QPS with a 90% cache hit rate.

Database QPS = 100,000 × (1 − 0.9) = **10,000 QPS**

Caching reduces database traffic by 90%.

Connection pooling manages database connections efficiently, while read replicas distribute read traffic across multiple database instances.

## 5. Geographic Distribution

### Why Distribute Servers Across Regions?

Serving users from nearby regions reduces network latency and improves availability.

Suppose a system needs 1,000 servers globally.

| Region | Traffic share | Base servers |
|---|---:|---:|
| US | 30% | 300 |
| Europe | 25% | 250 |
| Asia | 35% | 350 |
| Other regions | 10% | 100 |
| **Total** | **100%** | **1,000** |

This assumes server requirements scale with traffic. Each region also needs sufficient spare capacity to handle failures and traffic shifts.

## 6. Infrastructure Bottlenecks

QPS alone does not determine system capacity. A system can become limited by CPU, network bandwidth, memory, or storage.

| Component | What it measures |
|---|---|
| CPU | Processing capacity |
| Network bandwidth | Data transferred per second (e.g., Gbps) |
| Storage IOPS | Read/write operations per second |
| Memory | Data held in RAM |

Illustrative hardware references:
- Data center network: 10–25 Gbps.
- SSDs: Around 100K IOPS or more, depending on the device.
- HDDs: Roughly 100–200 IOPS.

These values vary by hardware and workload. Always identify the likely bottleneck rather than relying on generic benchmarks.

## 7. Cost Estimation

### Why Estimate Cost Early?

Infrastructure decisions affect both performance and operating costs.

Assume one server costs $100–$500 per month.

| Servers | Monthly server cost |
|---|---:|
| 100 | $10K–$50K |
| 1,000 | $100K–$500K |

These estimates cover servers only. Bandwidth, storage, databases, monitoring, and other services add to the total cost.

Improving efficiency can reduce infrastructure costs significantly at scale.

## 8. Interview Approach

Follow these steps:

1. **Estimate user activity:** Daily active users and requests per user.
2. **Calculate average QPS:** Daily requests / 86,400.
3. **Estimate peak QPS:** Apply a justified peak factor.
4. **Estimate server capacity:** Consider the workload and performance targets.
5. **Account for utilization and failures:** Include spare capacity.
6. **Identify bottlenecks:** Consider CPU, network, storage, and databases.
7. **Optimize database load:** Evaluate caching, connection pooling, and read replicas.
8. **Distribute capacity:** Account for regional traffic and redundancy.
9. **Estimate cost:** Calculate infrastructure and operating expenses.

**Key takeaway:** Estimate the load first, translate it into infrastructure requirements, and then account for real-world constraints such as peak traffic, utilization, failures, bottlenecks, and cost. The goal is a reasonable estimate supported by clear assumptions—not an exact server count.
