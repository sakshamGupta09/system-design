# System Design: 4-Step Framework

- If we are asked to build a system (example Twitter), How do we start?
- Follow this repeatable framework to approach any system design problem.

## The 4 Steps

1. **Gather Requirements** — Understand what to build.
2. **High-Level Design** — Identify the major components and how they interact.
3. **Detailed Design** — Design the critical components in depth.
4. **Scaling & Optimization** — Identify bottlenecks and make the system reliable and scalable.

---

## Step 1: Gather Requirements

**Why?** If you don't understand the problem, you might design the wrong system.

Clarify three things before designing.

### 1. Functional Requirements — What should the system do?

Identify the core features the system must support.

**Example: Twitter**
- Users can post tweets.
- Users can follow other users.
- Users can view their timelines.
- Users can like and retweet posts.

Focus on the essential features, not every possible feature.

### 2. Non-Functional Requirements (NFRs) — How well should it work?

Understand the expected performance and reliability.

- **Scale:** How many users and requests must it handle?
- **Latency:** How quickly should it respond?
- **Availability:** How much downtime is acceptable?
- **Consistency:** How fresh and accurate must the data be?

Clarify expected QPS, traffic patterns, and latency targets when relevant.

### 3. Constraints & Assumptions

Understand the boundaries of the problem.

- **Scope:** Is it a global or regional service?
- **Data:** Do we store text only, or images and videos too?
- **Retention:** How long should we keep the data?
- **Cost:** Are there budget constraints?

**Remember:** Write down the requirements and assumptions. They guide every decision that follows.

---

## Step 2: High-Level Design (HLD)

**Why?** Before designing individual components, you need to understand how the entire system fits together.

Identify the major components, draw them as boxes, and show how data flows between them.

### Common Building Blocks

- **Load Balancer:** Distributes incoming requests across servers.
- **Application Servers:** Execute business logic.
- **Database:** Stores persistent data.
- **Cache:** Keeps frequently accessed data for faster reads.
- **Message Queue:** Enables asynchronous processing.
- **Object Storage + CDN:** Stores and delivers images, videos, and other static content.

Use only the components your system actually needs.

### Example: Twitter

A simplified request flow:

1. The client sends a request.
2. The load balancer routes it to an application server.
3. The application server checks the cache.
4. If the data isn't cached, it fetches it from the database.
5. The response is returned to the client.

Media uploads may use object storage, while a queue can handle background tasks.

### Identify Core Workflows

Walk through the main operations to verify that your design supports them.

For Twitter:
- Posting a tweet.
- Generating a timeline.
- Following a user.

**Remember:** HLD is the big picture. Don't get distracted by database schemas, API details, or implementation code yet.

---

## Step 3: Detailed Design

**Why?** The high-level design shows that you understand the system. The detailed design demonstrates how you would actually build its critical parts.

Choose the components that are most important to the requirements, scale, or performance.

### What to Cover

**1. Database Design**
- What entities or tables/collections do we need?
- How are they related?
- Which queries must be fast?
- Which indexes support those queries?

**2. API Design**
- What endpoints are required?
- What inputs and outputs do they use?
- How should errors be handled?

**3. Core Logic**
- How does the main workflow work?
- Which operations are synchronous or asynchronous?
- What happens when multiple requests access the same data?

**4. Technology Choices**
- Which database, cache, or queue fits the requirements?
- Why is it suitable?
- What trade-offs does it introduce?

### Example: Twitter Timeline

There are two common approaches.

**Pull Model — Generate on Read**

When a user opens their timeline, fetch recent tweets from the users they follow.

- Advantage: Lower write cost.
- Disadvantage: Reads can be slow, especially for users following many accounts.

**Push Model — Generate on Write**

When someone posts a tweet, distribute it to their followers' timelines in advance.

- Advantage: Faster timeline reads.
- Disadvantage: More write operations and storage.

**Hybrid Model:** Combine both approaches. Push tweets from regular users and pull tweets from accounts with enormous followings when appropriate.

This balances read performance against write cost.

### Explain Your Trade-Offs

Never choose a technology just because it is popular.

Explain why it fits your requirements and what you sacrifice by choosing it.

For example, a relational database may suit transactional data, Redis may suit low-latency caching, and a distributed database may suit high-volume workloads. The right choice depends on the access patterns and requirements.

**Remember:** Go deep on the most critical components, not every component equally.

---

## Step 4: Scaling & Optimization

**Why?** A design that works for a small number of users may fail under heavy traffic or during failures.

Identify the bottlenecks first, then propose solutions.

### 1. Identify Bottlenecks

Ask yourself:
- Which component will struggle as traffic increases?
- Which queries or operations are expensive?
- Where could requests or data become unevenly distributed?
- What happens during traffic spikes?

### 2. Scale and Optimize

| Problem | Possible Solution |
|---|---|
| Too many requests on a few servers | Horizontal scaling + load balancing |
| Slow, repeated database reads | Caching + indexing |
| Database cannot handle the workload | Query optimization, replication, or sharding |
| Slow background tasks | Message queues + asynchronous processing |
| Large media files are expensive to deliver | Object storage + CDN + compression |
| Uneven traffic across partitions | Better partitioning and load distribution |

**Important:** Don't add every scaling technique automatically. Choose solutions based on the bottleneck you identify.

### 3. Reliability and Failure Handling

Consider what happens when a component fails.

- **Server failure:** Route traffic to healthy servers.
- **Cache failure:** Fall back to the database where feasible, with protection against overwhelming it.
- **Database or region failure:** Use appropriate replication, backups, and failover strategies.
- **Traffic abuse:** Apply rate limiting and traffic filtering.

### 4. Monitoring and Cost

**Monitor:** QPS, latency, error rates, resource utilization, and cache hit ratio.

**Optimize cost:** Right-size resources, compress or archive old data, and use lifecycle policies where appropriate.

**Remember:** Scaling is not just about handling more users. It's about maintaining performance, reliability, and reasonable cost as the system grows.

---

## Final Checklist

Before finishing, ask yourself:

- [ ] Have I clarified the functional and non-functional requirements?
- [ ] Have I drawn the major components and data flows?
- [ ] Have I explained the critical components in detail?
- [ ] Have I identified bottlenecks and discussed scaling?
- [ ] Have I considered failures, monitoring, and cost?
- [ ] Have I explained the trade-offs behind my decisions?
