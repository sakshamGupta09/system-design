# Functional Requirements (FRs)

- What a system should do from the user's perspective. What features and capabilities this system will offer to the users.
- Requirements should be clear, precise and should cover edge cases and failiure scenarios.
- Prioritize requirements into must-haves vs. nice-to-haves (MVP).
- FRs drive system design decisions. Missing a critical requirement can force costly redesigns.

## Clarifying Functional Requirements

Dig deeper into each requirement, ask questions and gain total clarity.

For example:
- **Message types:** Text, images, videos, or files?
- **Editing:** Can users edit sent messages?
- **Deletion:** Can users delete sent messages?

## How to Gather FRs

- **Identify users:** Who will use the system, and what can each user do? (e.g., buyers, sellers, and admins in e-commerce).
- **Define scope:** What must be included in the MVP, and what can wait?
- **Make requirements testable:** Replace "upload videos quickly" with "upload a 100 MB video within 2 minutes on a defined network connection."

## Hidden Functional Requirements

Look beyond the obvious features and ask, **"What should happen if…?"**

- If a user deletes a post, what happens to its comments?
- If User A blocks User B, what happens when A visits B's profile?

These overlooked scenarios can introduce important requirements and influence system design.

## Systems Evolve

- Requirements change as products grow — from text messages to emojis, images, videos, and files.
- **Anticipate likely future needs, but don't overengineer.** Make design decisions that allow reasonable evolution.
