# Document Databases

- A document database stores data as **documents (JSON-like objects)** instead of rows and columns like relational databases.
- Each document can have its own structure, and related information can be stored together in a single document.

**Example: E-commerce application**

A user document might look like this:

```
{
  "userId": 101,
  "name": "John",
  "email": "john@example.com",
  "addresses": [
    {
      "city": "Hyderabad",
      "type": "Home"
    },
    {
      "city": "Bangalore",
      "type": "Office"
    }
  ],
  "preferences": {
    "language": "English",
    "notifications": true
  }
}
```

Unlike SQL, we don't necessarily need separate tables for users, addresses and preferences.

**Popular example:** MongoDB.

## 2. Key Strengths

1. **Flexible Schema:** Documents don't need to follow an identical structure. We can add or remove fields without changing a fixed table schema.
2. **Natural Data Representation:** Data is stored in JSON-like format, making it easy for applications to work with.
3. **Fast Data Retrieval:** Related information can be stored together in one document, reducing the need for joins.
4. **Horizontal Scalability:** Data can be distributed across multiple servers using sharding to handle increasing data and traffic.
5. **High Availability:** Data can be replicated across multiple servers so the database can continue operating if one server fails.

## 3. How Does It Work?

Document databases organise data into three levels:

- **Database:** Contains collections.
- **Collection:** A group of related documents (similar to a table in SQL).
- **Document:** An individual JSON-like record (similar to a row in SQL).

**Example:**

An e-commerce database might contain:

- Users Collection → User documents
- Products Collection → Product documents
- Orders Collection → Order documents

Each document has a unique identifier, and we can retrieve, update or delete documents independently.

## 4. Real-World Use Cases

| Scenario           | Why document databases?                                   |
| ------------------ | --------------------------------------------------------- |
| E-commerce         | Products have different attributes and nested details.    |
| User profiles      | Users have different preferences, settings and addresses. |
| Content management | Articles have different structures and metadata.          |
| Social media       | Posts can contain text, images, comments and metadata.    |
| Gaming             | Player profiles, achievements and game settings vary.     |

## 5. When Should We Use Document Databases?

**Use when:**

- Data has flexible or frequently changing structures.
- Application data naturally fits JSON objects.
- Related information is frequently accessed together.
- Horizontal scalability is important.

**Avoid when:**

- Data has many complex relationships.
- Applications frequently need joins across multiple entities.
- Strong relational constraints and complex multi-entity transactions are central to the application.

---

**Remember:** Document databases store data as flexible, self-contained JSON-like documents. They are particularly useful when application data is naturally hierarchical and frequently accessed together.
